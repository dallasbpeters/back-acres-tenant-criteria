# Test tenant and Playwright walkthrough

Run from the project folder with the local Clerk **development** keys already configured:

```sh
npm run test:tenant:workflow
npm run demo:tenant
```

The first command runs the browser test and stops its servers. The second runs the same assertions, then keeps the isolated demo running at http://localhost:3193/demo. Stop it with Ctrl+C. The existing development server on port 3191 is unaffected. Ports 3193 and 3194 must be free. Install the browser video dependency once with `npx playwright install ffmpeg` if needed; the suite uses installed Chrome.

Development tenant: `back-acres-tenant+clerk_test@example.com`. Sign in with email code `424242`. This is a Clerk test email, not a real mailbox. The development instance currently requires organization membership; setup supplies the synthetic “Back Acres TEST household.” This does not grant owner access or change production Clerk settings.

The demo page includes fresh lease, invoice and automatic-payment links and a captured mailbox. Lease verification codes are generated by the application, **not** the Clerk code: request a lease code, then refresh the demo page to read it. Both lease signers are synthetic. No tenancy or payment obligation is created.

## What the browser verifies

- Real Clerk email-code sign-in against the development instance; empty account before owner assignment; owner and tenant permissions remain separate.
- Owner creates the property, invoices and finite ACH schedule through actual handlers. Only the tiny, explicitly non-contract lease draft is directly seeded.
- Owner assigns the verified account explicit invoice and schedule access. An unshared invoice stays hidden.
- Application-generated invitations and verification emails are captured locally. Both signers draw signatures, accept electronic-signature consent and sign the frozen document. The test checks timestamps, evidence, document hashes, both signature images, completed PDF export and PDF page count.
- Checkout submission remains processing until a correctly signed simulated settlement event arrives. Unsigned callbacks fail; duplicate settlement events produce one paid history entry.
- Payment consent gates bank setup. Simulated verified mandate creates a finite future schedule; accepted terms download matches the saved authorization. Stopping future payments cancels without proration or a new invoice.
- Shared payment history, maintenance submission visible to the owner, persistent phone settings, rejected writes to other tenancy IDs, revoked access, restored access, and sign-out protection.
- Fresh unsigned lease, open invoice and unstarted authorization are left for manual exploration. Completed paid history and maintenance records remain visible in the demo.

## Isolation and limits

The runner creates a disposable copy of the application in the ignored `tmp/` folder (Turbopack only compiles files inside the project root), applies every migration to an in-memory PGlite database, and substitutes the database and Stripe transports **only in that copy**. The transport substitutions never touch the production application files; there is no deployed test login, header bypass or test endpoint. The browser run separately exposed missing Clerk Protect CSP sources; the normal application policy now includes the documented script, frame and connection hosts. See [Clerk’s CSP requirements](https://clerk.com/docs/guides/secure/best-practices/csp-headers). Local sign-in uses the normal Clerk middleware and a development tenant. The owner's local session is generated with an isolated signing secret; this does **not** test Google's OAuth consent screen.

The runner uses an explicit environment allowlist. Real database URLs, Stripe keys, Resend keys, Vercel credentials and storage credentials are not passed to the isolated server. Clerk production keys are refused. Emails are redirected to a local captured mailbox with a strict recipient allowlist. Stripe HTTP calls go to a loopback simulator with explicit supported endpoints and fail on unsupported calls. The simulated payment page never accepts bank or card numbers. All database tables disappear when the demo stops; the synthetic Clerk development account and household persist for repeat runs.

This is an application end-to-end test with real Clerk development authentication and real SQL/signature/PDF/application routes. **Stripe Checkout, bank verification, settlement, Resend delivery and Neon transport are simulated.** It does not certify a real Stripe sandbox checkout, actual ACH settlement, email delivery, security compliance or legal enforceability. The existing Stripe unit/integration suite covers additional provider errors, refunds, disputes and recovery paths. Public application submission, lease generation questions, multi-tenant roommate scenarios and external identity-provider outages remain separate tests, not claims of this walkthrough.

Lease signing and payment setup currently arrive through private links; the tenant portal does not yet contain a lease archive or self-service bank replacement. Changes to bank accounts still require stopping the old authorization and asking the owner for a fresh link.

Artifacts are ignored by Git: HTML report in `playwright-report/tenant-workflow/`, video and signed PDF in `test-results/tenant-workflow/`, portal screenshot and local links in `output/`. Trace files on failure can contain development session credentials and private test links; keep them local. Never publish those traces or copy production keys into this fixture.
